## 2. New discovery — a seventh, previously unlisted entitlement/enablement-shaped field (OW-3, binding)

**`TenantFeature` (table `tenant_features`, model `app/infrastructure/db/models/org_feature.py`) is a real, live, tenant-scoped feature-enablement table not listed anywhere in `requirements.md` §2 or `design.md` §2.1's six-mechanism inventory.**

Shape: `tenant_id` (FK), `feature_key` (str), `enabled` (bool), `enabled_at`, `enabled_by` (FK → org_users), `metadata` (JSONB) — structurally close to what `TenantCapability` is designed to be.

**Exhaustive usage trace (every reference in `app/`, confirmed by full-repo grep):**
- **Writer:** `app/application/onboarding/go_live_service.py` (~line 592-609) — at tenant go-live, seeds one `TenantFeature` row per entry in `merged_config.get("enabledfeatures", [])` (the *same* template field as mechanism #4), `enabled=True`, once, idempotently (checks for an existing row first).
- **Reader:** `app/application/templates/tenant_data_service.py:_get_enabled_features` — returns the tenant's enabled `feature_key`s as one input (alongside staff/room/treatment/inventory counts) to `OnboardingProgressService.evaluate_step_completion` (`app/application/onboarding/progress_service.py`), which validates onboarding-wizard step completion against template `setupsteps` rules.
- **Consumers of that service:** `setup_progress_router.py`, `onboarding_router.py` only.
- **Confirmed NOT read by:** `get_tenant_features`, `PermissionSyncService`, or any other capability-gating/runtime-visibility code path — grepped and traced directly, zero matches outside the four files above plus model registration (`models/__init__.py`, `migrations/env.py`).

**Why this doesn't fold into R5, and why it still must be recorded (not silently dropped):**
This table answers a *different* question — "did the onboarding wizard enable this feature during setup" (a one-time, historical, onboarding-completion fact) — than R5's question, "is this capability available/enabled for use right now" (a live, continuously re-derived answer). It has zero overlap with the six mechanisms' actual runtime blast radius (`get_tenant_features`, `PermissionSyncService`). Its only consumers are the onboarding module, which is under independent, protected development (Codex) for the duration of this engagement — touching it would cross a boundary this whole effort has been explicitly instructed not to cross.

**Classification: (C) Not superseded this phase, explicit reason recorded** (see §3 table below). Recommendation only, pending T-A.4 approval — I have not modified `requirements.md`/`design.md`'s own text; the correction is recorded here per OW-3's own instruction ("shall be added to the ownership table before implementation proceeds"), not silently patched into the approved documents.

## 4. Outstanding item flagged forward to T-A.2

`design.md` §2.4's claim that "no code path was found that keeps [`OrgTenant.subscription_plan` and `OrgSubscription.plan_code`] in sync" and that `PermissionSyncService` is "the confirmed reader" of `subscription_plan` understates the actual surface. A shallow grep this session (not the full T-A.2 audit) already found `subscription_plan` read in `org_tenants_router.py`, `tenant_data_service.py`, `billing_notification_service.py`, `account_lifecycle_service.py`, `tenant_provisioning_service.py`, `sqlalchemy_repositories.py`, and `rbac_seed.py` — and *written* by `subscription_service.py`'s upgrade/downgrade flow and `account_lifecycle_service.py`, not just set once at creation. This is exactly the class of finding T-A.2 (subscription-plan-field reader audit) exists to enumerate exhaustively and decide the sync-vs-computed-projection disposition (FR-A3b) against — flagged here so T-A.2 starts from this corrected premise rather than `design.md`'s narrower one, not re-litigated or completed here (out of this task's scope).
