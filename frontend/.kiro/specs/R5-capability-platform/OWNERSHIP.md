## 2. Mechanism #7 — `tenant_features` / `TenantFeature` (OW-3, binding)

**`TenantFeature` (table `tenant_features`, model `app/infrastructure/db/models/org_feature.py`) is a real, live, tenant-scoped feature-enablement table not listed anywhere in `requirements.md` §2 or `design.md` §2.1's original six-mechanism inventory.** It is treated here as a full seventh mechanism, classified in the §3 table alongside the original six — not left as a standalone finding.

Shape: `tenant_id` (FK), `feature_key` (str), `enabled` (bool), `enabled_at`, `enabled_by` (FK → org_users), `metadata` (JSONB) — structurally close to what `TenantCapability` is designed to be, which is exactly why it needs explicit adjudication rather than a passing mention.

### 2.1 Evidence, point by point (each independently verified this session, not inferred)

- **Its only consumers are onboarding/readiness validation.** Full trace: `go_live_service.py` (writer) → `tenant_data_service.py._get_enabled_features` (reader) → `OnboardingProgressService.evaluate_step_completion` (`progress_service.py`) → consumed exclusively by `setup_progress_router.py` and `onboarding_router.py`. No other router or service touches it.
- **It is not read by runtime feature visibility.** `grep -n "TenantFeature\|tenant_features" app/application/services/org_tenants_service.py` (the module owning `get_tenant_features`, mechanisms #5/#6) returns only the unrelated method name `get_tenant_features` itself — zero reference to the `TenantFeature` model or `tenant_features` table.
- **It is not read by subscription entitlement.** `grep -rln "TenantFeature" app/application/billing/` → empty. No billing/subscription file references it.
- **It is not read by capability enforcement.** `grep -rln "TenantFeature" app/application/rbac/` → empty. No RBAC/permission-sync file references it (no capability-resolution code exists yet to check independently, since R5 hasn't shipped it — this is the closest available proxy: the *existing* enforcement-adjacent layer, RBAC, has zero coupling to it today).
- **It is not a live tenant-admin toggle.** `grep -rln "TenantFeature" app/api/` → empty — **no router, anywhere, exposes this table for read or write.** Its only writer (`go_live_service.py`) performs a one-time, idempotent, insert-if-absent seed at tenant go-live; grepping both usage sites confirms no code path ever sets `enabled=False` or otherwise updates an existing row — there is no toggle, only a one-shot creation.
- **It has no overlap with `get_tenant_features`, `PermissionSyncService`, or future capability resolution** — established by the three greps above, taken together.
- A fourth, initially-confusing signal was checked and ruled out: `templates_service.py`/`template_evaluation_service.py` also use a variable *named* `tenant_features` — read closely, this is an unrelated local `set[str]` built directly from `merged_config["enabledfeatures"]` for onboarding-wizard step/feature **visibility** rendering (`get_onboarding_template`), never touching the `TenantFeature` **table**. Naming coincidence, not a hidden second usage — recorded here so the coincidence doesn't get rediscovered and mistaken for new evidence later.

### 2.2 Ownership record

- **Owner:** the onboarding/readiness domain (not R5, not platform engineering-in-the-R5-sense).
- **Writer(s):** `app/application/onboarding/go_live_service.py` only — one-time, idempotent, insert-if-absent, at tenant go-live, seeded from `org_templates.enabledfeatures` (mechanism #4's own field).
- **Reader(s):** `app/application/templates/tenant_data_service.py` (`_get_enabled_features`) only, consumed by `app/application/onboarding/progress_service.py` for onboarding-wizard step-completion validation, surfaced only via `setup_progress_router.py`/`onboarding_router.py`.
- **Lifecycle:** created once per `(tenant_id, feature_key)` pair at go-live; never updated, never disabled, never deleted anywhere in the current codebase — a write-once historical snapshot, not a live-managed state.
- **Why this is a projection/readiness concern, not a capability authority:** it records a *historical fact about the onboarding process* ("this feature was turned on when the tenant went live, per the template in effect at that time") — it does not answer, and has never been asked to answer, "is this capability available/enabled for use right now." It has no dependency-graph concept, no entitlement-ceiling concept, no resolver, and is never re-evaluated after go-live. Authority for present-tense capability state belongs entirely to R5's own `TenantCapability`/resolver; this table's authority is scoped strictly to "what did onboarding do," past tense, once.
- **Binding boundary (recorded so it cannot be silently violated later):** `tenant_features` SHALL NOT be read by the Capability Resolver, `CapabilityService`, `CapabilityAdminService`, or any future capability-gating consumer. It SHALL NOT be treated as a second enablement source, a fallback, or a migration input for `TenantCapability`. Any future proposal to read it from R5-owned code is a scope change requiring its own explicit review, not an assumed extension of this classification.
- **Review trigger:** re-audit this classification when Codex's onboarding branch (`feature/progressive-experience-recovery` / `merge-progressive-phase0-into-test`) is integrated into `dev` — onboarding is under active, independent development for the duration of this engagement, and this table's usage could change before that merge lands. If the re-audit finds `tenant_features` has grown a new reader outside onboarding, or has started being consulted for anything resembling present-tense capability availability, it must be reclassified to (B) and brought into R5's reconciliation (Area G) at that time, per the reclassification rule below.

### 2.3 Reclassification rule

If any future evidence shows `tenant_features` represents live runtime feature state (read by `get_tenant_features`, by RBAC/permission-sync, by any capability-gating path, or exposed via a tenant-admin toggle), it must be reclassified **(B)** and folded into R5's Group F reconciliation — the (C) classification below is conditional on the evidence in §2.1 continuing to hold, not a permanent exemption.

### 3.1 `org_permissions.module` — explicit disposition (approved split)

- **The entitlement-filter interpretation is superseded and re-pointed by R5 — at both of its live call sites.** `PermissionSyncService.sync_tenant_permissions`'s `OrgPermission.module.in_(subscription_modules)` filter (§2.2 excerpt) **and** `rbac_seed.py`'s `_seed_tenant_permissions_async` raw-SQL equivalent (`op.module = ANY(:allowed_modules)`, T-A.2 finding) are both replaced by the new capability entitlement model, via `resolve_active_plan` + `SubscriptionPlanCapability` — the former via T-D.5a, the latter via T-D.5b — behind the flag, with both old paths kept live until Group F parity (T-F.1) passes (MIG-1). T-D.5c proves the two re-pointed paths produce equivalent results, closing the exact "two engines could silently diverge" risk a single-path re-pointing would have left open.
- **The RBAC admin/display interpretation remains, untouched, indefinitely.** `SQLAlchemyTenantPermissionRepository.list_by_tenant`/`get_by_id`'s use of `.module` (and `.category`) for admin permission-list filtering/display is an RBAC UI concern, not an entitlement concern (N-1) — R5 does not modify, deprecate, or plan to retire this usage. It is not on any removal criterion or deadline.
- **The column itself is not retired by R5.** `org_permissions.module` stays exactly as it is, schema-unchanged — only one of its two call sites (the entitlement filter) is superseded; the column's existence is never in question.
- **No capability toggle may mutate permission rows (binding, NFR-7).** `CapabilityAdminService` (T-D.2a) writes only `TenantCapability`; it never writes `org_permissions`, `tenant_permissions`, or `tenant_role_permissions` — enforced by the dedicated regression test `design.md` §15/§17 already specifies (the test proving the admin write path never touches those three tables). Recorded here explicitly so the `.module` split above is never misread as license to blur capability and permission state.

## 4. T-A.2 outcome (completed, approved) — `OrgTenant.subscription_plan` / `OrgSubscription.plan_code`

T-A.2's full exhaustive reader/writer audit is recorded in `tasks.md` under the T-A.2 task entry (six live writers of `subscription_plan`, two `plan_code` writers of which one is dead code, and the discovery that three of four live tenant-creation paths never create an `OrgSubscription` row at all). It is not duplicated here — this section records only the disposition and the corrections that audit produced, approved as of this amendment.

**`OrgTenant.subscription_plan` final disposition — phased, not immediate (revised language, was previously understated as more settled than it is):** the approved end-state is a **computed/read-only projection with no independent writers** — but this is a **future state reached in stages**, not a description of anything already implemented:
1. **During the migration window:** the field continues to be written by its six live call sites exactly as today (org-admin `PATCH`/`POST`, onboarding go-live, onboarding provisioning, `SubscriptionCheckoutService`, `TrialService.convert_trial_to_subscription`), and is read by exactly one new place — the active-plan contract's Tier 2 (`legacy_tenant_projection`, `design.md` §9.0, amended) — as an explicit, logged, temporary compatibility source.
2. **After reconciliation (T-C.2b, separately reviewed, not yet executed or even fully scoped):** consumers move to reading `resolve_active_plan`'s answer exclusively; Tier 2 usage (measured by `capability_active_plan_legacy_fallback_count`) trends toward zero.
3. **Final state (Group F, gated on parity proof):** the field becomes computed/read-only or is deprecated outright, with no independent writers remaining. `design.md`/`tasks.md` do not claim this state exists yet anywhere in the current documents.

**Both mandatory design corrections from this amendment are recorded:**
- §9.0/ADR-R5-03 amended for the migration-aware three-tier `resolve_active_plan` (`active_subscription` → `legacy_tenant_projection` → `minimum_fallback`), with an explicit binding constraint that the resolver never manufactures billing history — see `design.md` §9.0 and ADR-R5-03 directly.
- `rbac_seed.py`'s `_seed_tenant_permissions_async` added to the entitlement-writer reconciliation scope (§1/§3/§3.1 above), with T-D.5 split into T-D.5a (runtime re-sync)/T-D.5b (creation-time seeding)/T-D.5c (parity test) in `tasks.md`.

## 5. Engineering debt — dormant subscription code (recorded, not repaired)

Per required review: the zero-reachability finding for `SubscriptionService` (`app/application/billing/subscription_service.py`) and all trial-expiry enforcement (`TrialService._expire_trial`/`check_trial_status`/`get_expiring_trials`) is **accepted as engineering debt, not fixed or removed as part of T-A.2 or this amendment.**

- **Confirmed zero callers:** no router references `SubscriptionService`; its only importer, `BillingJobService`, imports it but never calls any of its methods (the sole reference is a stub comment, `"# This would use SubscriptionService to process renewals"`); `BillingJobService` itself has zero callers anywhere (no router, scheduler, or CLI entry point). Trial-expiry functions (`_expire_trial`, `check_trial_status`, `get_expiring_trials`) likewise have zero callers outside their own file.
- **Dormant drift bug, recorded:** `SubscriptionService.cancel_subscription` updates `OrgTenant.subscription_status` on cancellation but never touches `subscription_plan` — a stale-plan-code bug. It cannot execute today (the method is unreachable), so it is **not** a live production issue, but it is preserved here as a concrete illustration of exactly the failure mode ADR-R5-03's three-tier contract and its `source`/observability design exist to prevent.
- **Risk of reconnection:** if this code is ever wired up in the future (a router added, a scheduler configured) without first routing it through the approved active-plan/billing contract, it would reintroduce the exact `subscription_plan`/`OrgSubscription` drift this phase exists to close — and, because the code predates R5, it would do so by writing `OrgTenant.subscription_plan` directly rather than through `resolve_active_plan`.
- **Binding requirement for any future reactivation:** any future work that reconnects `SubscriptionService`, `BillingJobService`, or the trial-expiry functions to a live entry point **must** route their entitlement-relevant behavior through the by-then-shipped active-plan contract (or its Group F successor state) rather than resuming direct `OrgTenant.subscription_plan`/`OrgSubscription` writes independent of it. This is recorded here so that reactivating dead code is never mistaken for a low-risk change.
- **Not treated as proof of current billing behavior:** this debt record exists solely to prevent silent reintroduction of the bug; it does not imply the dead code represents how billing actually behaves today (it doesn't — it doesn't run at all) and is not used anywhere in this document as evidence for how live tenants are actually treated.
