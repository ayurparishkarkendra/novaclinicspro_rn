## 2. Mechanism #7 — `tenant_features` / `TenantFeature` (OW-3, binding)

**`TenantFeature` (table `tenant_features`, model `app/infrastructure/db/models/org_feature.py`) is a real, live, tenant-scoped feature-enablement table not listed anywhere in `requirements.md` §2 or `design.md` §2.1's original six-mechanism inventory.** It is treated here as a full seventh mechanism, classified in the §3 table alongside the original six — not left as a standalone finding.

Shape: `tenant_id` (FK), `feature_key` (str), `enabled` (bool), `enabled_at`, `enabled_by` (FK → org_users), `metadata` (JSONB) — structurally close to what `TenantCapability` is designed to be, which is exactly why it needs explicit adjudication rather than a passing mention.

### 2.1 Evidence, point by point (each independently verified this session, not inferred)

- **Its only consumers are onboarding/readiness validation.** Full trace: `go_live_service.py` (writer) → `tenant_data_service.py._get_enabled_features` (reader) → `OnboardingProgressService.evaluate_step_completion` (`progress_service.py`) → consumed exclusively by `setup_progress_router.py` and `onboarding_router.py`. No other router or service touches it.
- **It is not read by runtime feature visibility.** `grep -n "TenantFeature\|tenant_features" app/application/services/org_tenants_service.py` (the module owning `get_tenant_features`, mechanisms #5/#6) returns only the unrelated method name `get_tenant_features` itself — zero reference to the `TenantFeature` model or `tenant_features` table.
- **It is not read by subscription entitlement.** `grep -rln "TenantFeature" app/application/billing/` → empty. No billing/subscription file references it.
- **It is not read by capability enforcement.** `grep -rln "TenantFeature" app/application/rbac/` → empty. No RBAC/permission-sync file references it (no capability-resolution code exists yet to check independently, since R5 hasn't shipped it — this is the closest available proxy: the *existing* enforcement-adjacent layer, RBAC, has zero coupling to it today).
- **It is not a live tenant-admin toggle.** `grep -rln "TenantFeature" app/api/` → empty — **no router, anywhere, exposes this table for read or write.** Its only writer (`go_live_service.py`) performs a one-time, idempotent, insert-if-absent seed at tenant go-live; grepping both usage sites confirms no code path ever sets `enabled=False` or otherwise updates an existing row — there is no toggle, only a one-shot creation.
- **It has no overlap with `get_tenant_features`, `PermissionSyncService`, or future capability resolution** — established by the three greps above, taken together.
- A fourth, initially-confusing signal was checked and ruled out: `templates_service.py`/`template_evaluation_service.py` also use a variable *named* `tenant_features` — read closely, this is an unrelated local `set[str]` built directly from `merged_config["enabledfeatures"]` for onboarding-wizard step/feature **visibility** rendering (`get_onboarding_template`), never touching the `TenantFeature` **table**. Naming coincidence, not a hidden second usage — recorded here so the coincidence doesn't get rediscovered and mistaken for new evidence later.

### 2.2 Ownership record

- **Owner:** the onboarding/readiness domain (not R5, not platform engineering-in-the-R5-sense).
- **Writer(s):** `app/application/onboarding/go_live_service.py` only — one-time, idempotent, insert-if-absent, at tenant go-live, seeded from `org_templates.enabledfeatures` (mechanism #4's own field).
- **Reader(s):** `app/application/templates/tenant_data_service.py` (`_get_enabled_features`) only, consumed by `app/application/onboarding/progress_service.py` for onboarding-wizard step-completion validation, surfaced only via `setup_progress_router.py`/`onboarding_router.py`.
- **Lifecycle:** created once per `(tenant_id, feature_key)` pair at go-live; never updated, never disabled, never deleted anywhere in the current codebase — a write-once historical snapshot, not a live-managed state.
- **Why this is a projection/readiness concern, not a capability authority:** it records a *historical fact about the onboarding process* ("this feature was turned on when the tenant went live, per the template in effect at that time") — it does not answer, and has never been asked to answer, "is this capability available/enabled for use right now." It has no dependency-graph concept, no entitlement-ceiling concept, no resolver, and is never re-evaluated after go-live. Authority for present-tense capability state belongs entirely to R5's own `TenantCapability`/resolver; this table's authority is scoped strictly to "what did onboarding do," past tense, once.
- **Binding boundary (recorded so it cannot be silently violated later):** `tenant_features` SHALL NOT be read by the Capability Resolver, `CapabilityService`, `CapabilityAdminService`, or any future capability-gating consumer. It SHALL NOT be treated as a second enablement source, a fallback, or a migration input for `TenantCapability`. Any future proposal to read it from R5-owned code is a scope change requiring its own explicit review, not an assumed extension of this classification.
- **Review trigger:** re-audit this classification when Codex's onboarding branch (`feature/progressive-experience-recovery` / `merge-progressive-phase0-into-test`) is integrated into `dev` — onboarding is under active, independent development for the duration of this engagement, and this table's usage could change before that merge lands. If the re-audit finds `tenant_features` has grown a new reader outside onboarding, or has started being consulted for anything resembling present-tense capability availability, it must be reclassified to (B) and brought into R5's reconciliation (Area G) at that time, per the reclassification rule below.

### 2.3 Reclassification rule

If any future evidence shows `tenant_features` represents live runtime feature state (read by `get_tenant_features`, by RBAC/permission-sync, by any capability-gating path, or exposed via a tenant-admin toggle), it must be reclassified **(B)** and folded into R5's Group F reconciliation — the (C) classification below is conditional on the evidence in §2.1 continuing to hold, not a permanent exemption.

### 3.1 `org_permissions.module` — explicit disposition (approved split)

- **The entitlement-filter interpretation is superseded and re-pointed by R5 — at both of its live call sites.** `PermissionSyncService.sync_tenant_permissions`'s `OrgPermission.module.in_(subscription_modules)` filter (§2.2 excerpt) **and** `rbac_seed.py`'s `_seed_tenant_permissions_async` raw-SQL equivalent (`op.module = ANY(:allowed_modules)`, T-A.2 finding) are both replaced by the new capability entitlement model, via `resolve_active_plan` + `SubscriptionPlanCapability` — the former via T-D.5a, the latter via T-D.5b — behind the flag, with both old paths kept live until Group F parity (T-F.1) passes (MIG-1). T-D.5c proves the two re-pointed paths produce equivalent results, closing the exact "two engines could silently diverge" risk a single-path re-pointing would have left open.
- **The RBAC admin/display interpretation remains, untouched, indefinitely.** `SQLAlchemyTenantPermissionRepository.list_by_tenant`/`get_by_id`'s use of `.module` (and `.category`) for admin permission-list filtering/display is an RBAC UI concern, not an entitlement concern (N-1) — R5 does not modify, deprecate, or plan to retire this usage. It is not on any removal criterion or deadline.
- **The column itself is not retired by R5.** `org_permissions.module` stays exactly as it is, schema-unchanged — only one of its two call sites (the entitlement filter) is superseded; the column's existence is never in question.
- **No capability toggle may mutate permission rows (binding, NFR-7).** `CapabilityAdminService` (T-D.2a) writes only `TenantCapability`; it never writes `org_permissions`, `tenant_permissions`, or `tenant_role_permissions` — enforced by the dedicated regression test `design.md` §15/§17 already specifies (the test proving the admin write path never touches those three tables). Recorded here explicitly so the `.module` split above is never misread as license to blur capability and permission state.

## 4. T-A.2 outcome (completed, approved) — `OrgTenant.subscription_plan` / `OrgSubscription.plan_code`

T-A.2's full exhaustive reader/writer audit is recorded in `tasks.md` under the T-A.2 task entry (six live writers of `subscription_plan`, two `plan_code` writers of which one is dead code, and the discovery that three of four live tenant-creation paths never create an `OrgSubscription` row at all). **`OrgTenant.subscription_plan` final disposition — phased, not immediate (revised language, was previously understated as more settled than it is):** the approved end-state is a **computed/read-only projection with no independent writers** — but this is a **future state reached in stages**, not a description of anything already implemented:
1. **During the migration window:** the field continues to be written by its six live call sites exactly as today (org-admin `PATCH`/`POST`, onboarding go-live, onboarding provisioning, `SubscriptionCheckoutService`, `TrialService.convert_trial_to_subscription`), and is read by exactly one new place — the active-plan contract's Tier 2 (`legacy_tenant_projection`, `design.md` §9.0, amended) — as an explicit, logged, temporary compatibility source.

## 5. Engineering debt — dormant subscription code (recorded, not repaired)

Per required review: the zero-reachability finding for `SubscriptionService` (`app/application/billing/subscription_service.py`) and all trial-expiry enforcement (`TrialService._expire_trial`/`check_trial_status`/`get_expiring_trials`) is **accepted as engineering debt, not fixed or removed as part of T-A.2 or this amendment.**

- **Dormant drift bug, recorded:** `SubscriptionService.cancel_subscription` updates `OrgTenant.subscription_status` on cancellation but never touches `subscription_plan` — a stale-plan-code bug. It cannot execute today (the method is unreachable), so it is **not** a live production issue, but it is preserved here as a concrete illustration of exactly the failure mode ADR-R5-03's three-tier contract and its `source`/observability design exist to prevent.
- **Risk of reconnection:** if this code is ever wired up in the future (a router added, a scheduler configured) without first routing it through the approved active-plan/billing contract, it would reintroduce the exact `subscription_plan`/`OrgSubscription` drift this phase exists to close — and, because the code predates R5, it would do so by writing `OrgTenant.subscription_plan` directly rather than through `resolve_active_plan`.
- **Binding requirement for any future reactivation:** any future work that reconnects `SubscriptionService`, `BillingJobService`, or the trial-expiry functions to a live entry point **must** route their entitlement-relevant behavior through the by-then-shipped active-plan contract (or its Group F successor state) rather than resuming direct `OrgTenant.subscription_plan`/`OrgSubscription` writes independent of it. This is recorded here so that reactivating dead code is never mistaken for a low-risk change.
- **Not treated as proof of current billing behavior:** this debt record exists solely to prevent silent reintroduction of the bug; it does not imply the dead code represents how billing actually behaves today (it doesn't — it doesn't run at all) and is not used anywhere in this document as evidence for how live tenants are actually treated.

### 5.1 Engineering debt — full migration chain cannot be replayed from an empty database (found during T-B.1a)

**Accepted as release-relevant engineering debt, not repaired inside T-B.1a or any other R5 schema task.** T-B.1a's own verification (isolated `alembic stamp` + `upgrade`/`downgrade`) proves only *this migration's* correctness in isolation — it does **not** prove the complete Alembic history can build a database from zero, and that claim is not made anywhere in T-B.1a's completion report.

- **Failing revision:** `1d51109d8e2d` (`add_staff_bank_details_table`).
- **Exact failing operation/error:** `upgrade()` calls `op.drop_index('idx_tenant_rules_org_rule', table_name='tenant_appointment_rules')` (immediately followed by `op.drop_index('idx_tenant_rules_tenant_org_rule', ...)` and `op.drop_table('tenant_appointment_rules')`) — this raises `asyncpg.exceptions.UndefinedObjectError: index "idx_tenant_rules_org_rule" does not exist`, surfaced by SQLAlchemy as `sqlalchemy.exc.ProgrammingError`, when replayed against a database built from empty.
- **Proof this occurs before the R5 migration, not caused by it:** (a) empirically — a full `alembic upgrade head` run from an empty database halted at this revision and never reached `20260711_120000` (R4, the immediate prior head) or `20260712_120000` (R5's own T-B.1a migration); (b) exhaustively — `grep -rln "tenant_appointment_rules\|idx_tenant_rules_org_rule" app/infrastructure/db/migrations/versions/*.py` returns **only this one file** across all 117 migrations. No earlier migration in this repository's tracked history ever creates `tenant_appointment_rules` or its `idx_tenant_rules_org_rule` index — this migration's `upgrade()` assumes the table already exists from some out-of-band schema state (a manual creation, a pre-repository migration, or a squash that predates the current file set), not one this repo's own chain produces from empty. (This file's own `downgrade()`, at line ~1587, *does* `create_index('idx_tenant_rules_org_rule', ...)` — i.e., the create exists only in the reverse direction of the very migration that assumes it, confirming the asymmetry directly rather than inferring it.)
- **Impact:** a genuinely new environment cannot currently provision a database via `alembic upgrade head` from scratch — the full migration chain is not replayable on an empty database today. CI's own `alembic upgrade head` step (`ci-tests.yml`) evidently succeeds against its fresh `postgres:15` service container per job — **this discrepancy between the local from-scratch failure and CI's apparent success is itself unexplained** and not investigated further here (out of T-B.1a's scope); it is possible CI's Postgres has some difference in extension/session state, or this local finding needs independent reproduction in a CI-equivalent container before being treated as confirmed-broken-in-CI-too, rather than only confirmed-broken-in-this-local-replay.
- **Required resolution point:** before R7 production-hardening exit, and preferably before R5's own Group Z migration verification (T-Z.1's full regression pass) — whichever comes first. Not a blocker for any R5 schema task in the interim, since every R5 migration to date has been verified in isolation against the confirmed single prior head, independent of this earlier defect.

### 5.2 Engineering debt — a second, distinct pre-existing migration bug (found during T-B.1c, data-dependent, not the same defect as §5.1)

**Accepted as release-relevant engineering debt, not repaired inside T-B.1c or any other R5 schema task.** T-B.1c genuinely needs `org_tenants`/`org_subscription_plans`/`tenant_staff` to already exist (real FKs, unlike T-B.1a/T-B.1b's self-FK/single-new-table cases) — an isolated `alembic stamp` past those tables was not viable, so a clone of the existing, reachable, already-untouched `novaclinics_e2e` database (its own real alembic state, `05aec2bbf49c`, well behind R5) was tried as a way to get a realistic ancestor schema without a from-empty replay. That attempt surfaced a **second, independent** pre-existing bug — not the §5.1 defect, and not triggered by anything R5 changes.

- **Failing revision:** `d8f3a9b2c1e4` (`seed_casesheet_extension_templates`).
- **Exact failing operation/error:** an `INSERT` into `tenant_casesheet_templates` (as part of this migration's seed data) violates `chk_tenant_casesheet_templates_extension_has_parent` — `asyncpg.exceptions.CheckViolationError`, surfaced by SQLAlchemy as `sqlalchemy.exc.IntegrityError`.
- **Nature of the bug — data-dependent, not a from-empty-replay defect like §5.1:** this migration's own seed `INSERT` conflicts with **pre-existing row data already present** in the `novaclinics_e2e` database's `tenant_casesheet_templates` table at the point this migration would run against it — i.e., the migration assumes a data shape that doesn't hold for at least this one real environment. This is a different failure class from §5.1 (which is a from-empty schema-ordering bug, not data-dependent) — recorded as a **separate** item rather than folded into §5.1, since conflating them would misstate both.
- **Proof this is unrelated to R5:** `d8f3a9b2c1e4` and `chk_tenant_casesheet_templates_extension_has_parent` do not appear anywhere in any R5 migration (`grep` confirms zero references outside this one historical file); the failure occurred while attempting to advance a *clone* of `novaclinics_e2e` from its own pre-R5 state (`05aec2bbf49c`) toward head, entirely before any R5 migration would run.

## 7. Real-data finding — inactive `FREE` plan causes existing `FREE`-plan tenants to resolve to `minimum_fallback`, not their actual plan (found 2026-07-13, deployment checkpoint before T-C.5; **resolved same day**, see §7.1)

**Not a bug in this correction or in T-C.4d — surfaced by seeding real data into the previously-empty Supabase catalogue and exercising `CapabilityResolutionService.resolve_for_tenant` against a genuine, existing tenant, per the explicitly-requested pre-T-C.5 deployment checkpoint.** Recorded here rather than silently patched, since it touches already-approved T-C.2 behavior and the correct fix depends on a product/billing judgment call this document does not have the authority to make unilaterally.

**Observed:** on the configured Supabase database, `org_subscription_plans.FREE` has `is_active=False, is_public=False` (3 of the 4 seeded plans — `BASIC`/`PRO`/`ENTERPRISE` — are `is_active=True`; only `FREE` is not). **7 of this database's 9 tenants have `org_tenants.subscription_plan='FREE'`** and none of the 9 tenants has any `OrgSubscription` row at all (Tier 1 never qualifies for any of them — consistent with T-A.2's own finding that most tenant-creation paths never create one).

**Consequence, traced through `ActivePlanResolver._resolve_legacy_or_minimum` (T-C.2):** Tier 2's own validation query requires `OrgSubscriptionPlan.code == legacy_plan_code AND OrgSubscriptionPlan.is_active == True`. Since `FREE.is_active=False`, this query returns no row for any of the 7 `FREE`-plan tenants — `active_plan_resolver.invalid_legacy_plan_code_ignored` fires (as designed, for what the code calls "unknown/retired/typo'd" codes) and all 7 tenants fall through to `minimum_fallback`, resolving as if on no plan at all, rather than to `FREE`'s own (correct, real) `["CORE"]` entitlement ceiling. Verified live: resolving a real `FREE`-plan tenant's capabilities returned `source=minimum_fallback, is_minimum_fallback=True` and only 4 of 14 capabilities `effective_available` (the 4 `appointments`/`core` branch codes minimum-fallback also happens to grant, since `MINIMUM_FALLBACK_PLAN_CODE` is itself `FREE`'s own code — see next paragraph for why this makes the symptom easy to miss).

**Why this is subtle, not immediately obvious:** `MINIMUM_FALLBACK_PLAN_CODE` (T-C.2) is itself `"FREE"` — so a `FREE`-plan tenant hitting Tier 3 happens to resolve to the *same plan code* it should have gotten from Tier 2, **by coincidence**, not by design. The `source` field (`minimum_fallback` vs `active_subscription`/`legacy_tenant_projection`) is the only externally-visible difference — silently wrong provenance, not (for `FREE` tenants specifically) silently wrong entitlement. A `BASIC`/`PRO`/`ENTERPRISE` tenant whose plan row were ever deactivated the same way would NOT have this coincidental safety net and would visibly lose real entitlement.

**Two candidate readings of `is_active` were identified, genuinely different intents:**
1. `is_active=False` legitimately means "not a real, currently-honored plan" — a tenant assigned to a deactivated plan *should* fall to the floor.
2. `is_active` (per its own schema comment, `org_subscription_plans.is_active`: *"Whether this plan is currently available for new subscriptions"*) is about closing a plan to **new** signups, not about revoking entitlement from **existing** subscribers already on it.

**Not engineering debt in the R5-introduced-bug sense — a real-world data/design question R5's own resolver was the first mechanism ever built capable of surfacing it.** `PermissionSyncService` (the pre-R5 mechanism) does not check `is_active` at all in its own plan lookup (confirmed, T-A.1 §2.2) — meaning this exact scenario has been silently latent in the pre-R5 system too, just never visible, since nothing checked it. Flagged here as a genuine platform-maturity finding, not a regression this phase caused.

### 7.1 Resolution (approved 2026-07-13, same day as the finding)

**Reading (2) is the approved semantic rule, binding going forward:**

> `OrgSubscriptionPlan.is_active` means "available for new subscription selection, checkout, or upgrade." It does not mean "existing tenant assignments or active subscriptions referencing this plan are invalid."

**Fix applied to `ActivePlanResolver` (`active_plan_resolver.py`), Tier 2 only:** the plan-lookup query's `is_active == True` filter was removed — Tier 2 now validates the legacy `OrgTenant.subscription_plan` code by **plan existence only** (a real, present `OrgSubscriptionPlan` row with that code), never by whether the row is still open for new sales. Tier 1 required **no code change** — it was already correct (it never queries `OrgSubscriptionPlan` at all; an active/trial `OrgSubscription`'s own `plan_code` is authoritative regardless of the referenced plan's `is_active` value). Tier 3 (`minimum_fallback`) is now reached only when no matching plan row exists at all (a genuinely unknown/retired/typo'd code) — not merely when the matching plan has been closed to new signups.

**Verified against the real Supabase tenant that surfaced the finding:** re-resolving the same tenant (`org_tenants.subscription_plan='FREE'`, `org_subscription_plans.FREE.is_active=False`) now returns `plan_code=FREE, source=legacy_tenant_projection, is_minimum_fallback=false, warning=None` — no longer `minimum_fallback`. `capability_active_plan_resolution_source_count` observability (T-C.4d) confirmed reporting the corrected source. No Supabase plan data was touched — `FREE.is_active` remains `False`; the fix is entirely in how Tier 2 interprets it, not in the data itself. Row counts on all R5/tenant/plan tables confirmed unchanged before and after the fix (read-only verification).

**No plan-selection, checkout, or capability-entitlement behavior changed.** `SubscriptionService`/`SubscriptionCheckoutService` (the actual checkout-layer consumers of `is_active`) are untouched — confirmed by `git diff --stat` showing zero changes outside `active_plan_resolver.py` and its own tests. `capability_resolver.py` (the pure domain resolver) also untouched.

Full technical detail (compiled-query regression test, the 5 new/updated test scenarios, real-Supabase re-verification) in `tasks.md`'s dedicated correction entry.
